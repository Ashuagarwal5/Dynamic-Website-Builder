# Branches and tenants

Branches use only active memberships from backend GET /tenants. The table, cards, sidebar, and profile ignore local branch drafts, name overrides, deletion markers, and demo selections. Existing browser data is preserved for recovery but cannot affect branch visibility or selection. Backend branches previously hidden locally will reappear with their backend names.

Creation submits JSON { name, slug } to POST /api/tenants. The authenticated Route Handler validates input and returns safe JSON. On success the browser navigates client-side to Branches and refreshes memberships without reloading the document.

Edit is enabled in table and card views through PATCH /tenants/{tenantId}. The dialog collects name and slug only and calls the browser JSON route PATCH /api/tenants/{tenantId}. It validates current membership and exact input fields, returns safe errors, and refreshes the server membership list on success without a document reload. No local storage is used. Delete is enabled through backend DELETE /tenants/{tenantId} with a confirmation dialog. Status is integrated through PATCH /tenants/{tenantId}/status with a boolean isActive.

Switching uses the switchTenant Server Action to validate fresh memberships and save activeTenantId in the encrypted HTTP-only session. Branch selection no longer requires browser storage. Empty memberships show the empty state; failed reads do not fall back to local data.

Website listing and creation now use backend APIs only. Automatic local website migration was removed from SessionProvider. Legacy editor content remains separate until its API integration; old browser data is preserved.

Legacy branch-storage helpers remain disconnected from the active UI, with old data preserved.

The dashboard reads validated full memberships once through getTenantMemberships(). It passes active memberships for workspace access and full memberships for branch management. The Branches table has a Status control separate from Switch branch; card view offers Activate/Deactivate. Status changes require confirmation, use plain JSON through /api/tenants/{tenantId}/status, refresh backend memberships after success, and never use local storage. Inactive branches cannot be selected or edited until reactivated. Deactivating the selected branch makes active workspace resolution fall back to another active membership or no selection. Backend GET /tenants must return inactive memberships to allow listing and reactivation; if it excludes them, the backend must provide an authorized way to list them. Backend role checks remain authoritative. The supplied isActive payload needs no changes.

Tenant deletion uses browser DELETE /api/tenants/{tenantId} with no request body. The server checks session, origin, and fresh membership (including inactive tenants), then calls backend DELETE /tenants/{tenantId}. Successful responses refresh GET /tenants through router.refresh without a full page reload; there are no local deletion markers or local website checks. Backend rules decide whether the tenant can be deleted and what happens to related records. A rejected deletion keeps the row and displays a safe error. An uncertain network result is never retried automatically; the user is directed to refresh and check. Deleting the selected tenant falls back to another active tenant or no selection. No payload change is required for DELETE.
