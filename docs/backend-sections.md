# Backend sections

GET /tenants/{tenantId}/sites/{siteId}/pages/{pageId}/sections is integrated. Open My Websites, Pages, then Sections on a page row. A read-only panel lists sections ordered by sortOrder with type, content summary, visibility, and updated date. Hidden and unknown section types remain visible for management. HERO creation is integrated separately below. HERO updates are integrated separately below; section deletion is integrated below; bulk reorder remains pending.

The browser uses the matching /api/tenants/.../sections JSON route. The server validates the session and current branch membership. The backend must enforce the complete tenant/site/page relationship. Responses are validated for parent page ID, unique IDs, type, integer order, boolean visibility, config object, and timestamps. Only documented section fields are returned, preserving the whole config for later editing integration.

Loading, empty arrays, and retryable errors are handled without local storage. Late read results are ignored after closing or changing the panel instead of aborting fetch during cleanup. No backend request payload changes are required for GET.

Run npm run test:sections for transport, membership enforcement, safe field mapping, preserved config, ordering, hidden sections, malformed/cross-page response rejection, and upstream failures.

POST /tenants/{tenantId}/sites/{siteId}/pages/{pageId}/sections is integrated for the documented HERO schema. Open Sections then Create section. The form collects heading, subtitle, buttonText, buttonLink, sortOrder and isActive. Default order appends after the highest saved position. Shared client/server validation selects exact supported config fields, validates safe button links and types, and checks current tenant membership on the server. The browser sends plain JSON through the matching /api route. Successful creation refreshes the list in place without local storage or a document reload. Duplicate submissions are locked and uncertain failures are never retried automatically. Other section types remain readable but their create forms require confirmed creation schemas; this is intentionally limited to HERO. The supplied HERO payload needs no backend changes.

PATCH /tenants/{tenantId}/sites/{siteId}/pages/{pageId}/sections/{sectionId} is integrated for HERO editing. The Edit action pre-fills the shared form with content, order, and visibility. The browser sends plain JSON through the matching /api route. The server validates current membership and reads the latest section list to verify the section belongs to the page and is a supported HERO. It overlays validated editable config fields on the latest saved config and sends the full result, preserving unexposed fields under backend merge or replacement semantics. Successful updates refresh the section list in place without local storage or document reloads. Unknown types remain read-only. Conflicts and uncertain failures are surfaced without automatic mutation retries. This read-then-write does not provide atomic concurrency protection; backend revision/ETag support would be needed to prevent simultaneous editors overwriting the same fields. No payload change is required for the supplied HERO update schema.

DELETE /tenants/{tenantId}/sites/{siteId}/pages/{pageId}/sections/{sectionId} is integrated for all listed types, including hidden sections. Delete opens a confirmation dialog. The JSON route checks session, request origin, fresh branch membership, and presence of the section in a validated page section list before sending a body-free DELETE to the backend. The UI refreshes saved sections only after success; failures keep the dialog and row, and ambiguous failures are not retried automatically. If the deleted section was being edited, its editor is closed. No local storage or full document reload is used. No backend payload changes are required.
